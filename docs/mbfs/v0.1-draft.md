# MBFS v0.1 — Mooring & Berth Feed Specification (draft)

**Status: DRAFT, not published.** It lives here on purpose (docs/06 §A/S6): publishing a public
spec with zero implementers is a maintenance liability, and `GET /v1/opendata/mbfs` returns
`501 availability_not_enabled` until v2.

**Its v1 job is business development**: this is the document we put in front of a capitainerie or a
harbour-software vendor to ask *"could you send this?"*. Their answer is the M3 supply gate
([14](../14-roadmap.md)) — and it costs nothing to keep asking.

Rationale in [ADR-0004](../adr/0004-open-feed-spec.md), consumption rules in
[06 §B.4](../06-availability-strategy.md).

MBFS is deliberately GBFS-shaped: one open spec, implemented once per harbour-software vendor,
consumable by anyone. A vendor integrating MBFS unlocks every port they serve at once.

> **The minimum viable payload is one number.** A field with `num_free` and no per-berth detail is
> a *valid* MBFS document. That removes the two objections capitaineries actually raise: "I do not
> want to expose my customers' data" and "my system cannot do that".

## 1. Transports

A vendor picks **one**.

### (a) Pull — you host a document, we poll it

```
GET https://vendor.example/mbfs/v1/station_status.json
```

We poll every `ttl` seconds (never faster than 30 s), with `If-None-Match` when you send an `ETag`.

### (b) Push — you send us deltas or a snapshot

```
POST /v1/feeds/{feed_id}/observations     # deltas: only what changed
PUT  /v1/feeds/{feed_id}/snapshot         # full current state (simpler for most vendors)
Authorization: Bearer <token>
```

Tokens are issued per feed, hashed at rest, rotatable, and scoped to one `feed_id`. They are never
logged. Ask for one at `contact@balise.fr`; rotate with `balise-admin feed rotate-token <id>`.

## 2. Document

```json
{
  "last_updated": "2026-08-06T13:42:00Z",
  "ttl": 60,
  "version": "0.1",
  "data": {
    "harbours": [
      {
        "harbour_id": "FR-56-CROUESTY",
        "fields": [
          {
            "field_id": "PANNE-A",
            "capacity": 48,
            "visitor_capacity": 12,
            "num_free": 5,
            "last_reported": "2026-08-06T13:41:30Z",
            "spots": [
              { "spot_id": "A12", "state": "free", "max_loa_m": 12.0, "max_draft_m": 2.2 },
              { "spot_id": "A13", "state": "occupied", "until": "2026-08-09T10:00:00Z" }
            ]
          }
        ]
      }
    ]
  }
}
```

### Fields

| Field | Type | Required | Meaning |
|---|---|---|---|
| `last_updated` | RFC 3339 UTC | yes | When *you* computed this document |
| `ttl` | integer seconds, 1–3600 | yes | How long it stays valid; drives our poll cadence and staleness |
| `version` | string | yes | `"0.1"` |
| `data.harbours[]` | array | yes | One entry per harbour in this feed |
| `harbour_id` | string | yes | Your own identifier, stable over time |
| `fields[]` | array | yes | A `panne`, a mooring field, a visitor zone |
| `field_id` | string | yes | Your own identifier, stable over time |
| `capacity` | integer | no | Total places in the field |
| `visitor_capacity` | integer | no | Of which reservable by visitors |
| `num_free` | integer | no* | Free places right now — **this alone is enough** |
| `last_reported` | RFC 3339 UTC | no | When the field's state was measured (defaults to `last_updated`) |
| `spots[]` | array | no* | Per-place detail, when you can share it |
| `spot_id` | string | yes (in `spots`) | The berth number as painted on the pontoon, or your internal id |
| `state` | enum | yes (in `spots`) | `free` · `occupied` · `reserved` · `out_of_service` |
| `observed_at` | RFC 3339 UTC | no | When that place was measured |
| `until` | RFC 3339 UTC | no | For `reserved`/`occupied`: when it frees up |
| `max_loa_m`, `max_draft_m` | number | no | Place limits, if they differ from the field |

\* A field must carry `num_free` **or** a non-empty `spots` array. Neither means no availability
information, and the line is rejected.

## 3. How we consume it

| Rule | Behaviour |
|---|---|
| Identification | `spot_id` matches `spot.external_ids["{feed_id}"]`, or the painted `code` in your harbour |
| Rejections | Per line. An unknown `spot_id` never fails the batch: `{"accepted": 42, "rejected": [{"index": 7, "reason": "unknown spot_id"}]}` |
| Trust | A feed is weighted 0.95 and cannot declare itself higher |
| Supersession | Your latest reading replaces your own previous one — two readings never compete |
| Authority | Your freshest reading overrides community reports it contradicts, and is a confidence floor for those it confirms |
| Clock skew | `observed_at` is clamped to `[now − 24 h, now + 5 min]` |
| Staleness | No heartbeat for `3 × ttl` → your spots become **`unknown`**, and the app says *« données du port indisponibles »*. Never a stale green pin. |
| Snapshot absence | A spot absent from a snapshot ages out to `unknown` on the same rule |
| Privacy | We never store or display who is moored where. Only aggregate occupancy is published |

## 5. Reference implementation and validator *(v2 deliverable, prototyped)*

MIT-licensed, in this repository under `ingest/src/balise_ingest/mbfs/`. The validator is what a
vendor runs before we ever integrate; it is prototyped now so the BD conversation can be concrete,
and it is published with the spec in v2:

```bash
uv run balise-mbfs validate https://vendor.example/mbfs/v1/station_status.json
uv run balise-mbfs validate ./station_status.json
uv run balise-mbfs poll   https://vendor.example/mbfs/v1/station_status.json
uv run balise-mbfs push   --feed-id feed.port-crouesty --spot-id A12 --state free
uv run balise-mbfs health --feed-id feed.port-crouesty
```

The validator checks the schema, the clock, `num_free ≤ capacity`, duplicate `spot_id`s and expired
`until` values, and exits non-zero on anything that would be rejected in production.

## 6. Compatibility promise

- Additive changes only within `0.x`; anything breaking bumps the version and both are accepted
  during a 6-month overlap.
- A live feed is never broken by a change on our side.
- Deprecations are announced 6 months ahead via the `Sunset` header and the changelog.

## 7. What you get, in one line

We fill your visitor berths and cut the VHF calls; you send us one JSON file; you keep control and
can switch it off at any time.
